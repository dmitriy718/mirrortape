# MirrorTape follow-up production audit

## Inspected architecture and constraints

The clean `main` checkout is a Node 24/npm application with a package-lock. The active UI is React 19/TypeScript/React Router, styled with Tailwind and product CSS, built by Vite. Fastify provides session authentication, strict schema validation, provider integrations, health endpoints and the public HTML/asset server. PostgreSQL 16 stores users, sessions, versioned drafts, watchlists, pending undo state, rate windows, activity, reservations, support cases, provider connections, billing state, email jobs and audit records. Two checksummed transactional migrations define the current schema. No schema change is introduced in this audit increment.

Public routes are prerendered at build time. `/demo` keeps sample data in the browser; `/app` and private APIs enforce authentication. Password signup stores versioned agreement evidence. Google/Apple/Facebook identities use provider-bound state; Stripe webhooks and provider callbacks use their protocol-specific verification instead of browser CSRF. The public status endpoint exposes enabled capabilities without creating an account session.

The active VPS uses Docker blue/green application slots, loopback-only app ports, an isolated PostgreSQL container and Caddy. Host Node/systemd deployment files are alternatives and must not be used for this installation. Current Caddy configuration provides automatic TLS/HTTP/2, gzip/zstd, body limits, security headers, restricted forwarded-IP handling and retained hashed assets. No WebSocket feature is currently used. The container restart policy and graceful stop window are already configured.

Commands: `npm run lint`, `npm run build` (includes both TypeScript projects), `npm test`, `npm run test:e2e`, `npm audit --audit-level=high`, ShellCheck/Bash syntax, and the release/proxy tests. Playwright uses installed Chromium with desktop and Pixel 7 projects, a dedicated PostgreSQL test database, one worker and zero retries. Public smoke checks use read-only journeys; test customer messages and accounts remain isolated.

## Findings and implemented corrections

1. Contact and signup forms only retried a stale draft revision. The workspace fallback discarded local edits by loading the remote draft. The shared recovery now compares the last acknowledged draft, current tab and current server version. Disjoint edits combine; divergent fields are shown side by side and require an explicit choice. Writes still use server revision checks, including after review. A later conflict cannot silently overwrite data. Passwords and tokens remain excluded from drafts.
2. Contact topic selection had independent UI state and could drift from reconciled data. It now uses the shared draft. Topic query links apply once, and reopening the same topic does not reset an existing support request reference. Browser coverage verifies a repeat submission after navigation returns the original case.
3. Background maintenance and database closure were registered as independent close hooks, allowing the pool to close before pending jobs finished. Shutdown now explicitly stops/awaits maintenance before ending the pool. A real-database regression holds a maintenance query until close has begun. Chromium holds a real API request behind an advisory lock while the actual compiled process receives SIGTERM or SIGINT; shutdown must begin, finish that request, and exit with code zero.
4. Initialization failures before the normal startup block lacked controlled cleanup. Missing build artifacts now produce a bounded, structured failure without configuration values and close the database pool. A subprocess check verifies prompt nonzero exit and absence of credentials. The initial implementation triggered a TypeScript nullable-capture error; the binding was corrected before the build passed.
5. Deployment cleanup could stop the candidate even if restoring the previous routing failed. It now retains the candidate when restoration or previous-process readiness cannot be verified and reports a critical failure. Mapping restore is atomic, and interruption is covered before the mapping mutation. Same-release reruns verify routed HTTPS as well as the local process.
6. Added the requested top-level `deploy.sh`: defaults to read-only preflight, rejects unexpected arguments, and delegates to the existing Docker release implementation. Shared health helpers retain the 30-second production deadline. CI now checks wrapper/helper syntax and fault tests.

## Acceptance scope and evidence

The twenty requested feature behaviors remain mapped individually in [VERIFICATION.md](VERIFICATION.md). This pass strengthens F04/F05 and deployment/lifecycle safety rather than inventing another set of duplicate features. Genuine activity and limited-capacity messaging remain data/configuration-dependent. Address suggestions retain consent and manual fallback; production provider acceptance is not established by fixtures.

Local results and exact deployed commit/CI evidence are recorded in the implementation log after each gate finishes. Release fault tests use real loopback HTTP and isolated temporary files, with administrative commands simulated where needed. The candidate-retention assertions execute the actual production cleanup function under controlled failures. They do not establish a successful fault-injected production rollback or disaster recovery drill.

## Still outside a production-readiness claim

The live configuration inspected during this pass has SMTP, Stripe billing, Alpaca and Google/Apple/Facebook disabled. Actual credentials/provider approvals and successful live or sandbox acceptance are still required. Google address-provider configuration is likewise an external dependency. No secrets were printed, replaced or committed.

The broader copy-trading product, verified performance data, execution/risk controls, legal/operator review, support/privacy fulfillment, operational retention, off-site recovery and load/soak evidence remain separate unfinished requirements. Passing application tests does not remove those gaps or prove every possible defect absent. No "SYSTEM PRODUCTION-READY" declaration is made on the basis of this increment.
